Technology

What we use and why

Everything here is free for a hackathon project.

Three rules that keep it clean

  • Calculations live in web/src/lib/ as plain functions with no React in them.
  • Components only draw and handle clicks.
  • The NASA key is read only inside the server route and is never sent to the browser.

How we work

One step at a time

  1. Build the current step only.
  2. Check it with the validation listed for that step.
  3. Understand it. Everyone on the team can explain what it does.
  4. Commit when the team says so, with the suggested message.
  5. Record it in the step log: what we built, why, how, the result of each check, and anything the next person should know.
  6. Only then start the next step.

Steps 1 to 3 go in order and are built. After step 3 the work splits: the two front-end people share steps 4 to 12, the data person takes step 13, the AI person step 14, and the story person starts step 16 right away.

Step 1 · Front end · Committed

Scaffold the Next.js app in web/

What
An empty Next.js 16.4.6 application in web/, with React 19, TypeScript in strict mode, Tailwind 4, ESLint, the App Router and a src/ folder. No features.
Why
Every later step lives inside it. Doing it alone first means that when something breaks later, we know the base was sound.
How
From the repo root: 
npx create-next-app@latest web --ts --tailwind --eslint --app --src-dir --import-alias "@/*" --use-npm --disable-git
cd web
npm install
--disable-git stops the tool from creating a second git repository inside ours.
Result
  • npm run lint: no problems.
  • npm run build: compiled, the start page is built as a static page.
  • npx tsc --noEmit: no type errors.
  • npm run dev: the start page answers on localhost:3000.
  • web/tsconfig.json contains "strict": true. There is no web/.git. node_modules and .next are ignored by git.
Good to know
  • After cloning or pulling, run npm install inside web/ before npm run dev. node_modules is not in git.
  • Edits to src/app/globals.css do not show up in a running dev server. Stop it with Ctrl+C and run npm run dev again. Edits to .tsx files, including new Tailwind classes, show up at once. The production build is not affected.
  • Cache Components is switched on in web/next.config.ts. The tool does this by default. It does not matter for static pages. It changes how server-side data loading behaves, so check it again in step 13.
  • web/AGENTS.md is created by Next.js and recreated by npm run dev if deleted. It tells AI coding tools to read the Next.js documentation shipped in node_modules/next/dist/docs/, because this version differs from older ones. We keep it in git.
  • npm audit lists 7 moderate issues. All are in the lint tooling, which never reaches users. Left alone.
Understanding
  • Why a web/ subfolder: the repo holds two separate things, the Python pipeline and the web app. Vercel is told to build only web/.
  • App Router: each folder under src/app/ is a page address. page.tsx is the page, layout.tsx wraps all pages.
  • Server and client components: by default a component runs on the server and sends HTML. Anything interactive needs "use client" at the top of its file.
  • Strict TypeScript: the compiler refuses values that might be missing. It prevents the "undefined" errors that break demos.
  • npm run build: this is what Vercel runs. If it passes locally, the deploy almost always passes too.
  • package-lock.json: pins the exact version of every library, so all five laptops and Vercel install the same thing. It is committed.

Step 3 · Front end · Committed

Data contract, data files and loader

What
The data is now inside the web app, with a description of its format in TypeScript, a function that loads one country, and a temporary menu that proves it works.
Why
This is the contract between the pipeline and the app. Every number on screen will be read through it, so the format is written down once and checked when a file is loaded.
How
  • web/scripts/copy-data.mjs, run with npm run copy-data inside web/. It copies the 16 country files and report.json from data/out/ into web/public/data/, checks that every row holds 10 numbers, and writes index.json with the country list, row counts and the first and last year.
  • web/src/lib/types.ts: CellRow describes one row. COL gives the position of each value by name. VIIRS_FIRST_YEAR is 2012.
  • web/src/lib/data.ts: loadCountryCells downloads one country file, checks its format and remembers it, so going back to a country does not download it again.
  • web/src/hooks/useCountryData.ts: gives a component one of four states: idle, loading, ready with the rows, or error with a message.
  • web/src/components/DataCheck.tsx: the temporary menu. Step 5 replaces it.
  • The root .gitignore said data/, which also hid web/public/data/ from git. It now says /data/, which only covers the pipeline folder.
Result
  • npm run copy-data: 16 countries, 502,310 rows, 2001 to 2025.
  • npm run lint, npm run build and npx tsc --noEmit pass.
  • In a browser, on the production build: Germany shows 23,292 rows, Ukraine 140,342, Czech Republic 4,304. These equal the row counts of the pipeline files.
  • The test entry for a missing file shows: The data file "Atlantis.json" was not found.
  • Choosing two countries quickly, one after the other, ends on the second one.
  • Not tested yet: the message for a file with a wrong format. It gets a unit test in step 4.
Good to know
  • After the pipeline is rerun, run npm run copy-data and commit web/public/data/. The deployed site only has the data that is in git.
  • Read rows by name, not by number: row[COL.year], not row[2].
  • A viirsRaw of 0 before 2012 means "no data", not "no fire". The newer sensor did not exist yet.
  • The record starts in 2001, not 2000. That is 25 years, 2001 to 2025.
  • Size: web/public/data/ adds 27 MB to the repository. Ukraine is the largest file, 7 MB on disk and about 1.5 MB when sent compressed. It will take a moment on mobile data.
Understanding
  • The public folder: files in web/public/ are served as they are. public/data/cells/Germany.json is reachable at /data/cells/Germany.json.
  • Why one file per country: all countries together are 23 MB. The browser only downloads the one that is chosen.
  • Types as a contract: CellRow tells the compiler what a row looks like. A file is still checked when it is loaded, because the compiler cannot see the contents of a downloaded file.
  • Hook: a function whose name starts with use and that keeps state for a component. useCountryData hides the downloading, so a component only asks "what is the state now?".
  • "use client": the menu reacts to clicks and downloads data in the browser, so its file starts with "use client". The page around it is still built on the server.
  • Cancelling: when another country is chosen, the download that is still running is cancelled. Without this, a slow file could arrive late and overwrite the newer choice.

Step 4 · Front end 1 · Checked

Calculation library with tests

What
Plain functions that turn country rows into a year-by-month table and read statements from it: totals, the rank of a month, median and average, main season, worst year, a year against a typical year, and a trend test. Plus unit tests, run with npm test.
Why
Every number on screen comes from here. Keeping the calculations out of the components means they can be tested once, and steps 5 to 11 only draw what these functions return.
How
  • web/src/lib/stats.ts: general helpers with no knowledge of fire. sum, mean, median, normalCdf, and mannKendall: the Mann-Kendall trend test with tie correction, plus Sen's slope (the median change per year).
  • web/src/lib/calendar.ts: the fire calculations. buildTable(rows, {record, measure, firstYear, lastYear}) adds up all squares per year and month. record is "raw" (MODIS until 2011, VIIRS from 2012) or "corrected". measure is "count" or "frp". Then yearTotals, monthTotals, monthSeries, rankMonth, mainSeason, typicalYear, worstYear, compareYear, yearTrend and isEstimated.
  • Months are 1 to 12 everywhere, as in the data files.
  • Vitest 4.1 added as a dev dependency, with "test": "vitest run" in package.json. No configuration file: the functions need no browser, so the default Node setup is enough.
  • Four test files next to the code: stats.test.ts, calendar.test.ts, data.test.ts (the wrong-format messages left open in step 3) and pipeline-totals.test.ts.
Result
  • npm test: 4 files, 50 tests, all pass.
  • Check against the pipeline: for all 16 countries, the 2022 to 2025 totals equal actual_viirs and raw_modis in report.json.
  • Check against the prototype: the Germany table equals the prototype calendar on the project board for all four views (raw and corrected, detections and heat output), within the prototype's rounding to whole numbers.
  • Check of the trend test: p-values for small series and for Germany's yearly totals match values computed with scipy.
  • npm run lint, npx tsc --noEmit and npm run build pass.
Good to know
  • The typical year is the median of the year totals, as in the prototype. For an even number of years the median is the average of the two middle values. The prototype always had 25 years, so it never needed that.
  • Ties: mainSeason and worstYear prefer the earlier month or year, so the same data always gives the same statement.
  • Functions return null when there is nothing to say, for example the main season of an area with no fire. Components must show a sentence for that case, not a crash.
  • For step 10: Germany's corrected record also shows a significant rise (S = 184, p < 0.001), not only the raw record (S = 212). The planned check "the raw record shows a false rise that the corrected one does not" will need a country or region where that is true, or a different wording.
  • pipeline-totals.test.ts reads the real files in web/public/data/ and assets/proto/Germany.js. If it fails after a pipeline rerun, run npm run copy-data and rebuild the prototype data, or the numbers on the project board are out of date.
Understanding
  • Unit test: a small program that calls one function with known input and checks the answer. npm test runs all of them in under a second.
  • Median, not average: one extreme fire year pulls the average up a lot and the median hardly at all. The median is the fairer "typical year".
  • Mann-Kendall: counts how often a later year is higher than an earlier one, against how often it is lower. If "higher" wins by much more than chance would give, the trend is real. It assumes no straight line and is not thrown off by one extreme year.
  • p-value: the chance of seeing a trend this strong if there were none. Below 0.05 we call it significant.
  • Why the trend is only fair on the corrected record: in the raw record the counts jump in 2012 because the newer sensor sees about three times more. The test would report that jump as a rise in fire.

Step 6 · Front end 1 · Checked

Raw / corrected switch and date range

What
A Corrected / Raw switch above the calendar, with a sentence explaining each record. In the corrected record the years before 2012 have dashed boxes because they are estimates. A coloured line marks where the newer satellite starts. Two menus, From and To, choose the years shown.
Why
The switch makes the harmonization visible: in the raw record the totals jump at 2012, in the corrected one they do not. The date range is required by the challenge.
How
  • web/src/components/FireCalendar.tsx: holds the record and the year range. It builds both records for the chosen years and gives them one shared colour scale, as the prototype does. Otherwise each record would be scaled to its own maximum and the jump would be hidden by the colours.
  • The From menu lists only years up to To, and To only years from From, so the range can never be reversed.
  • The switch is two buttons with aria-pressed, so a screen reader announces which record is on.
  • web/src/components/CalendarGrid.tsx: dashed outline and the word "(estimated)" for screen readers on corrected years before 2012, and the line above 2012 when 2012 is not the first row shown. The cells carry data-estimated and the row data-split, which the tests read.
Result
  • Done-when check, in pipeline-totals.test.ts. "Jump" is the average of 2012 to 2014 divided by the average of 2009 to 2011.
    • Germany: raw 3.28, corrected 1.04.
    • All 16 countries added together: raw 2.56, corrected 0.81.
    • In every country the raw jump is exactly 3.16 times the corrected one. That is regional_ratio_all_cells in report.json, the ratio the pipeline ships, so the app shows the correction exactly as the pipeline made it.
  • Component tests: 132 cells (11 years × 12 months) marked estimated in the corrected record, none in the raw one. One line at 2012. A range of 2012 to 2015 shows 4 years and no line.
  • npm test: 79 tests pass. npm run lint, npx tsc --noEmit and npm run build pass.
Good to know
  • Single countries are noisy. Sweden's corrected record rises 1.67 times around 2012 and Turkey's raw record only 1.52 times, because real fire changed in those years too. Do not use those two to demonstrate the switch. Germany, Greece, Italy and France show it best.
  • The correction is one ratio for now. Before 2012 the corrected record is the MODIS count times 3.16. If step 14 ships a model instead, the ratio test above will fail on purpose. Replace it then.
  • Not done: the detections / heat output switch from the prototype. The data and buildTable already support it (measure: "frp"), so it is a small addition if the team wants it.
  • Changing the country keeps the record and the year range.
Understanding
  • Why the raw record jumps: the newer satellite, VIIRS, has smaller pixels and sees smaller fires, so it counts about three times more detections for the same fires.
  • What "corrected" means here: the older satellite's counts multiplied up to the newer satellite's scale, so the 25 years can be compared with each other.

Step 7 · Front end 2 · Checked

Map with fire squares

What
A map under the calendar with one coloured square per 0.25° cell. Without a picked month it shows the chosen years added up. Clicking a month in the calendar shows that month; clicking it again, or "Show all months again", goes back. The map follows the country menu, the record switch and the year range.
Why
Shows where the fire was, not only when.
How
  • web/src/lib/map.ts: squareValues adds up fire per square for the years or one month, viewBounds finds the area to show, squaresGeoJSON turns squares into polygons with a colour position t on the same square-root scale as the calendar.
  • web/src/components/FireMap.tsx: MapLibre GL 6.16.0 with the OpenFreeMap "positron" style (no key). MapLibre is imported only in the browser, after the component appears. If it cannot start (no WebGL), a message is shown and the calendar keeps working.
  • web/src/components/CalendarGrid.tsx: with onSelect each month is a button, with aria-pressed and a full description for screen readers. The picked month gets a solid outline.
  • web/scripts/copy-map-worker.mjs, run by predev and prebuild: copies MapLibre's worker to public/vendor/. That folder is ignored by git and by ESLint.
Result
  • Done-when check, on the data: in October 2017, 83% of Portugal's corrected detections lie in central Portugal (39.5 to 41°N, 8.75 to 7°W), and the five largest squares are all there, around 40.1 to 40.4°N. That is the area of the fires of 15 October 2017 in the Coimbra, Viseu, Guarda and Leiria districts.
  • Every country keeps at least 90% of its fire inside the first view.
  • npm test: 7 files, 103 tests pass. npm run lint, npx tsc --noEmit and npm run build pass. The worker is served at /vendor/maplibre-gl-worker.mjs.
  • Checked in Chrome (headless, with a screenshot): the map starts, Portugal is framed on the mainland, and after clicking October 2017 the darkest squares sit in central Portugal between Porto and Lisbon. No errors in the browser console.
Good to know
  • Why the worker is copied: MapLibre 6 looks for its worker file next to its own script. After Next.js bundles the script, that file is not there and the map stays empty. Setting the worker address to our own copy fixes it, on Vercel too, because prebuild runs there.
  • Version 6.16.0 is pinned on purpose. 6.18.0 was three days old when this was built.
  • Far islands are left out of the first view. Squares are split where there is a gap of more than 2°, and the group with the most fire is framed. Portugal opens on the mainland, not the Azores. Spain leaves out the Canary Islands, which hold 6% of its fire; they are still drawn and can be reached by moving the map.
  • Rotation is switched off, so north is always up.
  • The map needs an internet connection for the background tiles. The squares come from our own data.
  • No single detections as dots yet, which the prototype had. They need data the app does not have yet (see step 13).
Understanding
  • GeoJSON: the standard text format for shapes on a map. Each square is a polygon of five corner points, the last equal to the first.
  • Worker: a script that runs beside the page, so cutting map tiles does not freeze scrolling and clicking.
  • Why the map is loaded late: MapLibre needs window and WebGL, which do not exist while Next.js builds the page on the server.

Step 8 · Front end 2 · Checked

Region selection

What
A "Choose your own area" panel above the map: draw a rectangle or a polygon on the map, or type a south, north, west and east box. The calendar and the map then show only the squares whose centre lies inside the area, across borders. "Back to the whole country" returns to the menu's country; choosing another country does too.
Why
A selected area of interest is the central interaction in the challenge. Fire services work on districts, parks and forests, not countries.
How
  • web/src/lib/region.ts: Region is a box or a polygon. rowsInRegion keeps squares whose centre is inside, countriesInRegion finds every country file the area touches, parseBox reads the typed box and says what to fix, regionLabel names the area.
  • Regions cross borders. The Brandenburg box reaches into Poland. So a region loads every country whose area overlaps it, not only the menu's country. For that, each country in index.json now has bounds (west, south, east, north). scripts/copy-data.mjs writes them from now on; for the data already in git they were added with the same calculation, without touching the country files.
  • web/src/hooks/useCells.ts replaces useCountryData.ts: it loads one or several files and joins their rows. Each file is still downloaded only once.
  • web/src/components/RegionPanel.tsx: the draw buttons, a hint for the chosen tool, and the box form. Commas are accepted as decimal separator.
  • web/src/components/FireMap.tsx: terra-draw 1.38.0 with its MapLibre adapter 1.5.0 for drawing, and a dashed blue outline of the chosen area.
  • parseIndex in lib/data.ts checks index.json when the page is built, so a malformed bounds fails the build instead of the page.
Result
  • Done-when check: the box 51.35 to 53.56°N, 11.26 to 14.77°E loads Germany and Poland and gives 126 squares, the same as the prototype's "Brandenburg and Berlin area". Every month of both records equals the prototype within its rounding to whole numbers (region.test.ts). The same box drawn as a polygon selects the same squares.
  • In Chrome (headless, with screenshots): typing the box shows year totals 120, 281, 487, … against the prototype's 119, 281, 486, …; clicking two corners on the map draws a rectangle and the calendar recalculates. No errors in the console.
  • Fixed on the way: the data stores square centres rounded to two decimals (52.12 for 52.125), which left thin gaps and overlaps between squares on the map. snapToGrid puts them back on the exact 0.25° grid when drawing.
  • npm test: 8 files, 118 tests pass. npm run lint, npx tsc --noEmit and npm run build pass.
Good to know
  • No Turf.js. The technology table lists Turf for "which squares lie inside a region". pointInRing in region.ts does that in ten lines with tests, so no library was added.
  • Germany alone is not enough for Brandenburg: it gives 10,087 detections instead of 11,027. Nine border squares exist in both the German and the Polish file, each with that country's own detections, and both are counted.
  • A rectangle is stored as a polygon after drawing. Only the typed box is stored as a box. Both select the same squares.
  • The region is not in the page address yet. That comes with the shareable link in step 11.
  • Do not run npm run copy-data from a partial pipeline run. It replaces web/public/data/ completely.
Understanding
  • Point in polygon: draw a line from the point to the east and count how often it crosses the polygon's edges. Odd means inside, even means outside. It works for any shape, also with dents.
  • Why the square's centre decides: a square is either fully counted or not at all, because the data has no finer detail. Counting by centre is what the prototype did, so the numbers can be compared.

Step 9 · Front end 1 · Checked

Findings and comparison panel

What
Two boxes between the calendar and the map. "For fire services and forest managers" states the main season, the worst year and the latest year against a typical year. "Compare a month" appears when a month is clicked: how it ranks against the same month in every other year, its median and its average, and how far it is from the average. Both follow the country or region, the record and the year range.
Why
Turns the picture into statements a fire service can act on, and answers the challenge's "compare the current month against the historical median".
How
  • web/src/lib/findings.ts: describeTable and describeMonth return the sentences, built from the step 4 functions. Keeping the wording in lib/ means the exact sentences are unit tested.
  • web/src/components/FindingsPanel.tsx: shows them, with a warning in the raw record.
  • Rules in the wording: the typical year and month are medians; a change under 5% reads "about the same as"; corrected years before 2012 are marked "(estimated)"; with fewer than 3 years in the range no year is compared; an area without fire says so.
Result
  • Done-when check: the numbers were worked out by hand in Python from the data files, without the app's code, and findings.test.ts compares the full sentences:
    • Germany: April, July and August hold 46%; worst year 2025 with 3,935, 2.0 times the median of 1,982; 2025 is 99% above a typical year; July 2018 (882) is the highest July, against a median of 295 and an average of 332.
    • Brandenburg box (Germany and Poland): April, July and August hold 48%; worst year 2025 with 890, 2.4 times the median of 370; August 2022 (57) is above 10 of 24 Augusts and 19% below the average of 71.
  • In Chrome: the panel shows these sentences for Germany and July 2018. No console errors.
  • npm test: 9 files, 130 tests pass. npm run lint, npx tsc --noEmit and npm run build pass.
Good to know
  • 2025 is the worst year in both Germany and Brandenburg in the corrected record. That fits the step 4 note: the corrected record rises over the 25 years too. Step 10 has to show this honestly.
  • "Latest year" is the last year in the chosen range, not always 2025.
  • The prototype said "Latest full year, 2025". Once step 13 adds the current year from the daily feed, a part-year must not be compared with full years.
Understanding
  • Median and average side by side: one huge fire month pulls the average up but not the median. When the two differ a lot, the month's history has rare extreme years.
  • "More than 10 of 24": the rank among the other years. 24 of 24 is a record.

Step 10 · Front end 1 · Checked

Trend, extent and frequency views

What
Two charts under the findings, and a second way to colour the map.
  • Trend: yearly totals as bars, a dashed trend line, and one sentence: rising, falling or no clear trend, with the p-value. In the raw record it warns that the 2012 jump looks like a rise.
  • Extent: how many map squares had fire in each month, with a line where the newer satellite starts.
  • Frequency: "Colour squares by: Years with fire" colours each square by how many of the chosen years it burned, with a sentence such as "Half of the 660 squares with fire burned in at least 21 of the 25 years".
Why
The challenge names seasonal patterns, anomalies and trends. A trend is only fair on the corrected record, and this view shows why.
How
  • web/src/lib/trends.ts: trendOf (totals, Mann-Kendall test and Sen's line), describeTrend, extentByMonth, burnFrequency, describeFrequency and extentCaution.
  • web/src/components/EChart.tsx: Apache ECharts 6.1.0, loading only the bar and line charts, grid, tooltip, mark line and screen-reader description. Colours follow light and dark mode.
  • web/src/components/TrendsPanel.tsx: the two charts and their sentences. Estimated years are lighter bars.
  • The frequency view uses a straight (linear) colour scale; the amount view keeps the square-root scale. squaresGeoJSON takes the scale as an option.
Result

Good to know
  • For the pitch: in 8 of 16 countries the raw record shows a significant rise that is not there after correction, and in 2 more a rise turns into a fall. That is the strongest single argument for the harmonization. Germany is the exception: its rise is real.

Extra · Weather context · Checked

Historical weather context (ERA5)

What
A "Historical weather at one point" panel under the map. Choose a point on the map, a day and an hour (UTC); it shows ERA5 wind at 10 m in plain language, temperature and humidity at 2 m and the precipitation of the hour before, a slider through the day, a chart of the day's wind speed, and an arrow on the map pointing where the wind blows to. A picked calendar month limits the date picker to that month, but the day and hour are always chosen explicitly.
Why
Lets users see the wind around historical fire observations. It is context only: no fire prediction, spread, cause, ignition probability or arrival time, and it never changes fire counts or the harmonization.
How
  • web/src/lib/weather.ts: request URL (Open-Meteo archive API, models=era5, timezone=GMT, km/h, °C, mm), strict response check (units, UTC, 24 hours of the right day, missing values kept as null), wind from/to conversion, 16-point compass names, UTC timestamps.
  • web/src/lib/weatherApi.ts: WeatherCache, one request per point (rounded to 0.01°), day and model; shared in-flight requests; failures are not cached. currentWeather shows a result only for the key it was loaded for.
  • web/src/hooks/useWeatherDay.ts and useHistoricalWeather.ts: loading, cancelling and the point / day / hour state.
  • web/src/components/WeatherPanel.tsx: the panel. FireMap.tsx: point picking (click) and the arrow marker. Picking a point and drawing a region switch each other off.
Result
  • Open-Meteo checked live on 14 November 2026: models=era5 is accepted (an unknown model is refused), CORS allows calls from the browser, and the answer names the ERA5 grid point used.
  • In Chrome: Portugal, October 2017, a point near 40°N 7.75°W, 15 October 12:00 UTC shows wind from the southeast (143°) towards the northwest at 18 km/h, 28 °C, 26% humidity; the arrow points to 323°. At 18:00 it turns to 333°. Moving the slider makes no new request. Starting a region drawing switches picking off.
  • npm test: 12 files, 162 tests (35 new for weather). Lint, type check and build pass.
Good to know
  • Terms: the free Open-Meteo API is for non-commercial use only, under 10,000 calls a day per IP, data under CC BY 4.0. Requests go from each visitor's browser, so Vercel's shared IP does not count. Attribution to Open-Meteo and the Copernicus Climate Change Service is in the panel.
  • ERA5 is a reanalysis on a ~25 km grid: no local gusts or terrain winds. The panel says so and names the grid point used.
  • Not linked to step 11's shareable link yet: the weather point, day and hour are not in the page address.

Deployment

Vercel, before submission

The team decided on Saturday to build first and deploy at the end, as part of step 16. Until then npm run build is our check: it is the same command Vercel runs.

Do not leave it to the last hour. A first deploy often needs one fix, for example a setting or a secret that is missing. Plan it for Sunday morning, so there is time before the 16:00 deadline.

  1. The repository must be reachable by the Vercel account. On the free plan, connect it with the repository owner's account.
  2. In Vercel choose New Project, import the repository and set Root Directory to web. The framework is detected as Next.js.
  3. Secrets are set in Vercel under Settings, Environment Variables. Locally they go in web/.env.local, which is never committed.
  4. Every push to main builds production. Every other branch gets its own preview link. A preview link may ask for a Vercel login. The production link is public.
  5. Test each deploy in a private window and on a phone.
