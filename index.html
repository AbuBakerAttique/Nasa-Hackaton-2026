Problem statement

Nobody can say whether this month's fires are normal

NASA satellites have spotted fires from space by their heat since 2000. But the record comes from two generations of sensor.

  • MODIS, the older one, has blurry vision (1 km). It misses small fires and is close to retirement.
  • VIIRS, the newer one, has sharp vision (375 m). It has been flying since 2012 and sees about three times as many fire detections.

So the numbers jump in 2012 even when nothing changed on the ground. It is like counting birds by eye for years and then switching to binoculars. Fire services, forest managers and scientists cannot compare the old years with the new ones.

Our solution, in plain words

One fair record, shown as a calendar

  1. Collect. We download NASA's free fire records for both sensors.
  2. Learn the difference. For the years when both sensors watched the same fires, a model learns how the older one's counts relate to the newer one's.
  3. Correct the past. We apply that to the years before 2012, so all 25 years are on one scale.
  4. Prove it. We hide the last four years from the model and check how well it predicts them.
  5. Show it. A website draws a calendar for any region: years down the side, months across the top, darker means more fire.
  6. Flag it. The site says how the latest month compares with history.

How a user will use it

Five steps, no training needed

  1. Open the website. It starts on Brandenburg with a calendar already showing.
  2. Draw your own area on the map, pick a preset region, or type a latitude and longitude box.
  3. Read the calendar. You see the fire season, the worst years and how this month compares with the past.
  4. Flip the switch between the raw record and the corrected record to see what the correction changes.
  5. Download the numbers as a spreadsheet file.

Who it is for: fire services, forest managers, civil protection and researchers.

What happens inside 02_harmonize.py

  1. Clean. Keep vegetation fires only and drop low-quality detections. Factories and steelworks also show up as heat, so they are removed.
  2. Group. Lay a grid of squares (about 25 km) over the map and count detections per square and month, for each satellite.
  3. Learn. For 2012 to 2021, when both satellites were flying, a model learns how the old satellite's count relates to the new one's.
  4. Check. For 2022 to 2025, which the model never saw, compare its estimate with what the new satellite really recorded.
  5. Correct. Apply the model to 2001 to 2011, so every year is on the new satellite's scale.
  6. Export. Write the result as cells.json.

Why there is no server

The corrected record is small (about 3 MB), so the website can load it directly and do all the work in the browser. That means nothing to keep running, nothing to pay for, and nothing that can be asleep when a judge opens the link.

Which countries we use, and why

The pipeline now covers 16 European countries. The first test used four. The choice is ours, not a NASA requirement.

  • Germany is our local story: Brandenburg forest fires, for judges in Cottbus. But Germany has too few fire detections to train a model alone.
  • Portugal, Greece and Spain are among the most fire-affected countries in Europe. They supply enough examples for the model to learn from, including extreme years such as 2017 in Portugal.
  • Twelve more were added for coverage and for a fairer test: Italy, France, Croatia, Turkey, Poland, Czech Republic, Austria, Hungary, Sweden, Bulgaria, Romania and Ukraine.
  • Not the whole world. Very large fire countries such as Brazil and Russia are about 100 MB per year each. They are left out so the pipeline stays fast.

The list is at the top of pipeline/01_download.py. Accuracy differs by country, so the results section below reports Germany separately.

How to run the project

Data pipeline

python3 -m venv venv                         # once
venv/bin/pip install -r requirements.txt     # once
venv/bin/python pipeline/01_download.py      # NASA files into data/raw/ (skips files already there)
venv/bin/python pipeline/02_harmonize.py     # writes data/out/
venv/bin/python pipeline/03_build_prototype_data.py   # refreshes the prototype on this page (assets/proto/)

The second script writes four files into data/out/:

  • cells.json: the data the web app reads.
  • report.json: the accuracy numbers.
  • problem.png and validation.png: the two charts for the pitch.

Format of cells.json

Each row is one map square (0.25°) in one month:

[cell_lat, cell_lon, year, month, modis_raw, viirs_raw, harmonized]

viirs_raw is 0 before 2012 because the sensor did not exist yet. The app must show that as "no data", not as "no fire".

Results so far

Run on 16 countries, Saturday afternoon

Methods were fitted on 2012 to 2021 and tested on 2022 to 2025, which they never saw. "Fit" is R²: 1 is perfect, 0 is useless.

MethodFit for regional monthly totalsError on Germany's total
No correction (old satellite as it is)0.50about one third of the true count
One ratio for all countries (multiply by 3.16), shipped0.94+4.5%
One ratio per country0.94+11.9%
Machine-learning model per map square0.90-59.1%

What this means. The correction works: the fit for regional monthly totals rises from 0.50 to 0.94. The simplest method is currently the best, so that is what cells.json uses.

The machine-learning model is better for single map squares where the old satellite saw fire (average error 5.91 against 6.39). It is much worse for whole regions in low-fire countries such as Germany, because it cannot yet account for fires the old satellite missed entirely. Making it beat the simple ratio is the AI engineer's main task.

Known limit. All methods underestimate low-fire countries such as Austria, Poland, Sweden and the Czech Republic by 20 to 50%. The per-country numbers are in data/out/report.json.
